Part I

Orientation

01How to read this plan

This is the engineering companion to the Molehill Madness design document (v0.10). The design document says what the game is; this says what gets built, in what order, and how we know each step actually worked. Design decisions are cited as (GDD §n) and are not re-argued here.

Where it actually is, 30 August 2026

Phases 0 and 1 are complete, and most of 2, 3 and 4 is built along with half of 5. The tables below carry a Done on every task that is finished and a note on every one that is part done, so the plan can be read as a record rather than only as an intention.

The work did not happen in the plan's order, and the ordering was the plan's main argument. "Nothing downstream of a gate is started before the gate passes: no relay before the game is fun, no content money before the tech is proven." The relay, both paces, accounts, matchmaking, the clip pipeline, the whole arsenal and four Android releases all exist. The Phase 2 fun proof has no record: no playtest of four humans is written down anywhere, and there is no docs/phase-2-gate.md beside the Phase 0 one.

That is worth stating plainly rather than quietly re-drawing the diagram, because the fun gate is the one checkpoint this plan gives permission to kill the project cheaply, and it is now the only thing on the critical path that a build cannot answer. Either it passed and went unrecorded, or it was skipped. If it was skipped, everything downstream was a bet rather than a decision, and the bet is still open.

The other honest gap is teaching. Cutting the solo modes cut the tutorial with them, the drawn paw that stood in for one has been removed, and 4.7 now has nothing in it. The plan calls that the highest-risk UX in the project and it is currently unanswered.

The plan is organised as seven phases with two hard gates. A phase is a coherent chunk of work with explicit exit criteria; a gate is a phase whose exit criteria are allowed to kill or redirect the project. Phases map onto the design document's milestones (Phase 0 and 1 build toward M0, Phase 2 is M0, Phase 3 is M1, and so on), but they cut the work by engineering dependency rather than by feature list.

There are no dates anywhere in this document, deliberately. Tasks carry relative sizes instead: S roughly an evening or two, M a week of spare-time work, L several weeks, XL a phase-dominating effort. Sequencing and honesty about size are worth more than a schedule that would be fiction by October.

02Ground rules and assumptions

  • One programmer, part-time. The plan assumes a single experienced C#/.NET developer working evenings and weekends, new to Godot but not to shipping software. Every phase is sized so that one person can hold the whole thing in their head.
  • Art and audio are bought, not learned. Two contracted art packages (§15) and licensed audio. Programmer art is the standard until Phase 3, and the plan never blocks code on art.
  • The sim is the product; Godot is a lens (GDD §16). MoleSim is a plain C# library with zero engine dependencies, built and tested before the engine renders a single frame. This is the load-bearing architectural rule and every other choice defers to it.
  • Determinism is never retrofitted. Fixed-point maths from the first commit, replay-hash tests from the first playable sim, cross-platform hash checks from Phase 0. The design document calls determinism drift "fatal to online" (GDD §20) and this plan treats it that way.
  • Playtests are milestones, not celebrations. Phases 2, 3 and 4 each end with a structured test on real people, and the fun-proof gate is empowered to send the project back to the drawing board cheaply.
  • Windows is the whole dev box. iOS is out of scope until after the MVP (GDD §21), so no Mac, no Apple Developer Program and no second signing pipeline. This is the single largest scope saving in the plan: it removes a hardware dependency, an annual fee, a platform review process and an entire leg of the determinism matrix.
  • Scope guards from the design document hold here too: no solo modes, no AI, no map editor, no ranked, no fifth seat, no text anywhere. Nothing in this plan builds toward a cut feature.

04The sim contract

MoleSim's public surface is small on purpose. If the API below stays honest, everything else in the project stays cheap: the client is a renderer, the relay is a courier, replays and clips are free.

// create once per match, identically on every client
var match = MoleMatch.Create(mapBlob, seed, playerCount);

// planning: the UI builds a Plan (a list of timestamped input events)
// and the sim validates it (stamina, bedrock, fire-in-air, one reset)
match.SubmitPlan(seat, plan);            // throws on illegal input

// resolution: 240 ticks at 30 Hz, deterministic, replayable anywhere
RoundResult result = match.ResolveRound(); // events: hits, KOs, crates
ulong hash = match.StateHash();            // for CI + cheat verification

Rules the library holds itself to, checked by tests and analyzers rather than by discipline:

  • Fixed point everywhere. One Fix64 struct (Q48.16: 64-bit value, 16 fractional bits, ~0.015 mm precision at the game's 5 cm cell size), with deterministic Sqrt, Sin, Cos from lookup tables. A banned-API analyzer fails the build on float, double, System.Random, DateTime and Dictionary iteration inside the sim project.
  • One RNG, owned by the match. Seeded xoshiro256**; every draw goes through it in a defined order. Crate contents, bounce jitter and knockout-animation selection are all draws (GDD §8), so replays are bit-exact down to the pratfall.
  • Order independence where the rules promise it. The collision and pickup solvers iterate seats in index order but resolve symmetrically, and a property test permutes seat order on the corpus and asserts identical outcomes, because "no initiative, ever" (GDD §8) is a testable claim.
  • Plans are versioned binary. A hand-rolled writer with a leading version byte; target under 1 KB per plan (GDD §14). Old clients reject newer versions loudly. The relay stores payloads as opaque blobs and never parses them.
  • Hashing is cheap by design. Entities hash every tick; terrain keeps a rolling hash updated per carve, with a full re-hash at round end as the cross-check. Hashing must never be the reason the corpus is slow.
  • The tick fits the budget. Bench target: a full 240-tick, 4-player round resolves headless in under 50 ms on the dev box and under 250 ms on a 2020 mid-range phone, because ghost previews, instant replays and the clip renderer all re-run the sim constantly (GDD §16).
Design rule

Damage-ends-input (GDD §8), lava strikes (GDD §9) and reset-token validation (GDD §7) are sim rules, not UI behaviours. The client may draw whatever it likes; it cannot make an illegal thing happen, which is also the v1 anti-cheat story.

Part II

The phases

05The phase map

Four workstreams run through seven phases. The sim leads, the client follows one phase behind, content joins at the vertical slice, and online work starts only after the game is proven fun, because a relay for a game nobody wants to rematch is the most expensive way to learn that.

Tech gate · passed

The simulation computes byte-identical results on Windows, Linux and Android: combined hash D1096413CA1B6CF8 across two CPU architectures and two .NET runtime versions. The ARM64 result is the one that counts, because x86-64 against ARM64 is exactly where IEEE 754 arithmetic diverges in practice, and that boundary is the entire reason the sim is integer-only. The probe runs in 22 ms at 60 fps on a Mali-G78, against a 250 ms budget, so the plan's reliance on cheap re-simulation is affordable rather than hopeful.

Both questions answered, and the gate is clean. It was briefly half-answered: Godot reports that Apple Embedded export with C#/.NET is experimental and requires macOS, so iOS could not be attempted from a Windows machine at all. That is no longer a hole in the gate, because iOS is out of scope until after the MVP (GDD §21). Steam and Android, cross-play between them, one dev machine.

Three things the gate caught that would otherwise have been assumed: Godot 4.7.2's Android export template accepts net9.0 only though its own editor assemblies are net8.0; Android export needs ETC2/ASTC enabled; and Godot wants a classic .sln where .NET 10 now writes .slnx, without which the export silently produced a signed APK containing no C# at all. Full write-up in docs/phase-0-gate.md.

Part III

How it stays true

13Determinism, testing and CI

The whole architecture rests on every device computing the same match. That is not a property you check occasionally; it is a treadmill the pipeline runs every day.

  • Merge rules: sim changes require corpus green on Windows and Linux in CI; the Android corpus run is a scheduled nightly on a real device (manual button-press early, automated via a device farm when it earns the cost). A release build requires all three.
  • Every fixed bug becomes a replay. No exceptions. The corpus is the project's institutional memory.
  • Field telemetry closes the loop: from Phase 4, clients report a match-end state hash with the match id. Any disagreement between participants is a determinism bug caught in the wild with a perfect reproduction attached, because the match log is the repro.
  • Perf budgets are tests: the bench project asserts the tick budget (§04), viewport frame times, and clip render throughput, so a regression fails a build instead of a playtest.
  • Playtest cadence: every phase from 2 onward ends with humans, and the two UX bets (wordless HUD, first-round teaching) are tested on people who have never seen the game, never on us.

14Tooling that pays rent

  • The divergence bisector (Phase 1, not later): given one match log and two platforms' per-tick hashes, it finds the first divergent tick and dumps a structured state diff. Determinism debugging without this tool is despair; with it, it is a diff.
  • The headless CLI runs matches from scripted plans at thousands of rounds a minute: balance smoke tests (does Fracking dominate?), crate-spawn fairness histograms, stamina-economy sweeps across the cost table.
  • Sim inspector overlay in the client (F3): entity states, material ids under the cursor, tick scrubber over the last resolution, hash of the current state on screen.
  • Replay theatre is built as a dev tool in Phase 3 and becomes the player-facing feature in Phase 5 unchanged, because it was always just the sim plus a camera.
  • Map baker turns layered art files into terrain bitmaps with material ids, and validates them: reachability, spawn fairness, minimum diggable fraction, lava clearance.

15Content pipeline

  • Two contracted art packages. Package A (engaged during Phase 2, delivered through Phase 3): style guide, mole rig and animation set, the eight knockout exits, HUD glyph set and hand-drawn numerals, Garden biome. Package B (Phase 5): Allotment and Building Site biomes, cosmetics batch one, store capsules. Every glyph is reviewed at quarter-screen TV, phone size, and portrait-clip size before final rendering (GDD §17).
  • Animation format: skeletal (Godot's own or Spine, decided with the artist in Package A negotiation) for moles and exits, flipbooks for effects. The knockout reel is the one place frame-by-frame hand animation is worth the money, because those 1.2 seconds are reused in every clip and every trailer forever.
  • Audio: licensed brass-band-adjacent library plus contracted stings at Phase 5; the underground low-pass filter and the Boiling Point churn are bus effects, built in-house in Phase 3.
  • Maps are content, not code: hand-drawn layers baked by the tool, so new maps after launch cost art time only.
  • Names generator: a curated corpus of mole names, platoon names and Mole of the Match title fragments, written early, reviewed for every shipped language since generated text is the one text the game shows (GDD §18).

18The first ten tickets

The plan above starts with these, in order, starting tomorrow. Tickets 6, 7 and 9 are the whole reason Phase 0 exists.

  1. Create the repo with the §03 skeleton; CI builds and runs an empty test suite on push.
  2. Fix64: arithmetic, comparisons, deterministic Sqrt; property tests against reference values.
  3. xoshiro256** wrapped as MatchRng; sequence tests pinned to known vectors.
  4. Terrain bitmap: material ids, circle carve, rolling hash, PNG dump utility.
  5. Install and pin Godot 4.x; commit a C# scene with a placeholder mole walking on a flat floor.
  6. Export ticket 5 to a real Android phone; record fps and pain points.
  7. Toy sim: gravity, walking, one projectile; 240 ticks; state hash at the end.
  8. Run ticket 8 on Windows and on the Android device from ticket 6; compare hashes across ten seeds.
  9. Write the Phase 0 gate memo: proceed as planned, or reopen the engine decision with evidence attached.
The one habit that matters
